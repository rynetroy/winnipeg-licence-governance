# Governance Charter: Winnipeg Business Licence Data

Version 0.1, November 4, 2026. Personal project on public data. Not affiliated with or endorsed by the City of Winnipeg.

## 1. Purpose

Make every figure this project publishes about City of Winnipeg business licences defensible: traceable to a specific snapshot, produced by code, and built on definitions and standards that are written down. Where the data cannot support a decision, say so.

## 2. Scope

| In scope | Out of scope |
|---|---|
| City of Winnipeg Open Data dataset `d5k3-sfzx` (Business Licenses) | The City's source system and internal processes |
| Snapshots pulled by this project (CSV export 2026-04-04, API pull 2026-11-04 onward) | Related datasets, such as Short Term Rental Accommodations |
| The pipeline in `src/`, the metadata in `metadata/`, reports in `reports/` | Businesses that need no City licence (most businesses) |
| Planned Phase 2 outputs (data model, Power BI report) | Decisions made by others using City data |

## 3. Roles

There are two layers. The **source layer** belongs to the City. The **project layer** is the copy of the data this project pulls, transforms and publishes.

| Role | Layer | Held by | Responsibility |
|---|---|---|---|
| Source data owner | Source | City of Winnipeg licensing business area (not named on the portal; NEEDS EVIDENCE) | Accountable for the licence records and what they mean |
| Source publisher | Source | City of Winnipeg open data portal | Publishes the dataset and its metadata |
| Project data owner | Project | Troy Dela Rosa | Accountable for every published project output |
| Project data steward | Project | Troy Dela Rosa | Definitions, standards, quality rules, issue log |
| Project data custodian | Project | Troy Dela Rosa | Snapshots, pipeline, local storage, access to raw data |
| Data consumer | Project | Readers of the repository and reports | Use outputs within the stated limits |

**Separation of duties:** one person holds all three project roles, which a real organization would avoid. Compensating controls: raw snapshots are never edited, every figure is regenerated by code, and results are checked on a second machine (file hash plus a rerun with identical output) before publishing.

## 4. Decision rights

| Decision | Authority (decides) | Must consult | Recorded in |
|---|---|---|---|
| Accept a new snapshot into the project | Custodian | Steward | `pull_metadata.json`, decision log |
| Change a business definition (for example "active licence", "downtown") | Owner | Steward | Data dictionary, decision log |
| Add, change or retire a quality rule or threshold | Steward | Owner | Quality rules, decision log |
| Change a field mapping or the canonical schema | Steward | Custodian | `field_mapping.csv`, decision log |
| Classify a field's sensitivity | Owner | Steward | Data dictionary, decision log |
| Publish an output (report, README figure, dashboard) | Owner | Steward, Custodian | Commit history |
| Add a new data source | Owner | Steward, Custodian | Charter scope table, decision log |
| Correct the source data | Source data owner (City) | Not this project's decision | Issue log (reported upstream) |

## 5. Standards

1. **Raw is immutable.** Snapshots are saved once with their pull metadata and never overwritten or edited.
2. **Raw stays local.** Raw records are not published in the repository. Outputs show counts only for Sensitive fields.
3. **One canonical schema.** All sources are read through `load_snapshot.py` into snake_case field names from `field_mapping.csv`.
4. **Codes are text.** Identifiers and codes (such as neighbourhood numbers) are never stored as numbers.
5. **Dates are ISO** (`YYYY-MM-DD`). Validity is always judged against the snapshot date, not today.
6. **Every published figure is reproducible** from a named snapshot by code in this repository. Anything not yet verified is marked NEEDS EVIDENCE.
7. **Definitions are labelled by source.** Where the City publishes none, the project's working definition is used and labelled as such.

## 6. Change control

1. **Propose:** describe the change and why (for example "treat neighbourhood codes as text").
2. **Assess:** which outputs, rules or figures it affects. Rerun on both snapshots and compare.
3. **Decide:** by the role with authority in section 4.
4. **Record:** add an entry to `governance/decision_log.md`, then commit with a message that names the change.

## 7. Proposed roles and controls at the source (recommendations, not current practice)

Based on gaps found in this project, the City would gain most from:

1. A **named data owner and steward** on the dataset page.
2. **Field definitions** for all 13 fields (currently none).
3. A **unique licence identifier**, so duplicates can be told apart from separate licences.
4. A **published redaction policy**, applied consistently across licence families.
5. A **changelog** for scope or structure changes, such as the 2010 history and new licence families added between April and November 2026.
6. A **code list** for licence families, activities and statuses.

## 8. Review

The charter is reviewed when a new snapshot is accepted, when a new deliverable starts, or when a decision in section 4 changes a standard.
